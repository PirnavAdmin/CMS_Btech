# Academic fee plans and Student Admission — API contract

Implemented on 31 October 2026 for the uploaded .NET 8 backend and `dump now(3).sql` schema. Frontend changes are outside this backend package.

## Deployment

1. Back up the target database.
2. Select the existing database in MySQL Workbench and run `Database/Sql/Fees/AcademicFeePlans_20261031.sql` in full. The separately supplied SQL file is identical.
3. Build and run `BTech.csproj` using the existing connection string, JWT and CORS configuration.
4. Use an authenticated account with an active college assignment and the permissions below. No existing permission grants are widened by this SQL.

This is a direct SQL schema migration, not an EF migration. MySQL 8.0.16 or later is required. It adds four InnoDB tables and the nullable `studentadmissions.AcademicStudentCategory` column. The script is repeatable on the inspected schema. It does not rewrite old fee structures, admissions, passwords, roles or permissions, and does not convert browser-local plans into shared plans. DDL auto-commits. Deploy SQL before the new API; the new code expects these tables. A pre-existing table with the same name but a different schema must be reviewed separately because CREATE TABLE IF NOT EXISTS does not repair schema drift.

## Authentication and college authorization

All routes require `Authorization: Bearer <accessToken>`. College ownership, active users, active role assignments and active role permissions are checked from the database. A stale JWT role cannot grant approval. The existing middleware verifies any mapped College Admin college selection; the fee services use that verified scope. Every plan query includes college ownership. A role or action is never granted merely by supplying collegeId.

| Operation | Module permission | Additional role restriction |
| --- | --- | --- |
| List, get, history | fees / view | Active non-student role |
| Create draft or new version | fees / create | Active non-student role |
| Edit draft, submit | fees / edit | Active non-student role |
| Approve, return to draft, publish, archive | fees / edit | COLLEGE_ADMIN or PRINCIPAL |
| Admission picker and saved snapshot GET | student_admissions / view | Active non-student role |
| Admission create / update | student_admissions / create or edit | Existing admission permission rules |

An active SUPER_ADMIN retains explicit full-system access, with a college selection for each plan operation. COLLEGE_ADMIN has no unconditional bypass. STAFF or custom roles may create/edit/submit only when explicitly granted the required actions, and cannot approve/publish by claiming an elevated role in a token.

## Routes

Base: `/api/v1/academic-fee-plans`.

| Method | Route | Input |
| --- | --- | --- |
| GET | base | collegeId, optional status, page (default 1), pageSize (default 50, max 100) |
| GET | `/{feeStructureId}` | collegeId query |
| GET | `/{feeStructureId}/history` | collegeId query; ordered revision audit including snapshotJson |
| POST | base | Full draft body below; server always creates DRAFT |
| PUT | `/{feeStructureId}` | Full draft body plus expectedRevision; DRAFT only |
| POST | `/{feeStructureId}/submit` | collegeId query and transition body |
| POST | `/{feeStructureId}/approve` | collegeId query and transition body |
| POST | `/{feeStructureId}/return-to-draft` | collegeId query and transition body with reason |
| POST | `/{feeStructureId}/publish` | collegeId query and transition body |
| POST | `/{feeStructureId}/archive` | collegeId query and transition body |

Successful responses use `{ "success": true, "data": ... }`. Create returns HTTP 201 and a Location header. List also returns page/pageSize. The response contains `feeStructureId`, `version`, `revision`, `status`, all plan fields, the component list, the complete payment schedule and audit timestamps/users. `feeStructureId` is generated by the database from the existing `fee_structures` table; it is never a browser ID. The plan's public code is stored separately from the globally unique internal legacy structure code.

### Draft body

Replace the example IDs with real IDs from the same college's lookup APIs. Semester must belong to the course, branch and academic year.

```json
{
  "collegeId": 95,
  "code": "BTECH-CSE-2026-S1-MGMT",
  "name": "BTech CSE Semester 1 — Management quota",
  "academicYearId": 45,
  "courseId": 29,
  "branchId": 24,
  "semesterId": 214,
  "feeCategoryId": 1,
  "batch": "2026-2030",
  "quota": "Management",
  "studentCategory": "General",
  "cycle": "SEMESTER",
  "paymentMode": "INSTALLMENTS",
  "currencyCode": "INR",
  "effectiveFrom": "2026-06-01",
  "effectiveTo": "2027-05-31",
  "dueDate": "2027-01-10",
  "totalAmount": "54000.00",
  "components": [
    { "code": "TUITION_FEE", "name": "Tuition Fee", "amount": "50000.00" },
    { "code": "ADMISSION_FEE", "name": "Admission Fee", "amount": "4000.00" }
  ],
  "installments": [
    { "number": 1, "dueDate": "2026-11-10", "amount": "27000.00" },
    { "number": 2, "dueDate": "2027-01-10", "amount": "27000.00" }
  ]
}
```

- Required scope: college, academic year, course, branch, semester, batch and financial feeCategoryId. IDs must be active and form the same academic mapping.
- `feeCategoryId` identifies an existing financial category in `fee_categories`; `studentCategory` and `quota` describe eligible applicants. They are separate concepts.
- `cycle`: SEMESTER, ANNUAL or ONE_TIME. All cycles retain an explicit semester scope; ANNUAL does not silently match every semester.
- `paymentMode`: FULL_PAYMENT or INSTALLMENTS. This describes the payment schedule, not the payment collection channel such as cash/UPI.
- FULL_PAYMENT requires dueDate. Send installments as `[]` or a single matching schedule entry; the server stores one entry for the complete total.
- INSTALLMENTS requires 2–100 positive entries, numbered consecutively from 1 in chronological due-date order. Every due date must be inside the effective range, and dueDate must equal the last installment's date when supplied.
- Money uses C# decimal and MySQL DECIMAL(12,2), with no binary floating-point arithmetic. JSON amounts may be decimal strings or numbers. Maximum is 9999999999.99 with at most two decimal places. Component amounts must be nonnegative, total must be positive, and component/installment sums must equal totalAmount exactly. Component codes are unique ignoring case.
- String limits: code 80, name 150, batch 50, quota/category 100, component code/name 50/150; component count max 100.
- Code and version lineage cannot change during edits. PUT requires the current expectedRevision.

### Status workflow and versioning

Transition request:

```json
{ "expectedRevision": 3, "reason": "Reviewed by finance and approved" }
```

| Current | Allowed next states |
| --- | --- |
| DRAFT | SUBMITTED, ARCHIVED |
| SUBMITTED | APPROVED, DRAFT |
| APPROVED | PUBLISHED, DRAFT, ARCHIVED |
| PUBLISHED | ARCHIVED |
| ARCHIVED | None |

Returning to DRAFT requires a reason. Every successful edit or transition increments revision and appends an audit entry in the same transaction. Only DRAFT content can be edited. Expired plans cannot be published; future-effective published plans remain hidden until their start date.

To revise a published plan, POST a complete draft with the same code and `previousFeeStructureId` equal to the published/archived source ID. The server assigns the next version and a new feeStructureId. One successor is allowed per version. Approval/publication must be repeated. Two published versions of the same code in the same college cannot overlap in effective dates. Archive the old version before publishing an overlapping replacement. Distinct codes may offer alternative valid plans.

## Admission picker

`GET /api/v1/student-admissions/fee-plans`

Required query: `collegeId`, `academicYearId`, `courseId`, `branchId`, `semesterId`, `batch`. Include `quota` and `studentCategory` for a restricted applicant scope.

```http
GET /api/v1/student-admissions/fee-plans?collegeId=95&academicYearId=45&courseId=29&branchId=24&semesterId=214&batch=2026-2030&quota=Management&studentCategory=General
Authorization: Bearer <token>
```

The response contains full plan objects with components and installments. It includes only PUBLISHED plans effective on the server's current UTC date. College/year/course/branch/semester match exactly; batch matches after trimming, ignoring case. A nonblank plan quota/category must match the applicant's corresponding value; an omitted applicant value does not match a restricted plan. A null/blank plan quota/category explicitly means unrestricted for that dimension. No matching plans returns `data: []`, with no hardcoded fee fallback.

## Save an admission with the selected server plan

Existing routes remain:

- `POST /api/v1/student-admissions`
- `PUT /api/v1/student-admissions/{admissionId}`

Add the following fields to the existing admission body, along with its existing required personal fields:

```json
{
  "collegeId": 95,
  "academicYearId": 45,
  "courseId": 29,
  "branchId": 24,
  "semesterId": 214,
  "batch": "2026-2030",
  "admissionQuota": "Management",
  "studentCategory": "General",
  "feeStructureId": 123,
  "feePlanVersion": 1
}
```

`123` is illustrative: use the feeStructureId returned by the picker. feePlanVersion is optional; if provided for a new assignment it must equal the selected version. Nested `formData.fees.feeStructureId` / `structureId` numeric aliases are supported, but every supplied ID must agree. `FS-STANDARD`, UUIDs and other local IDs return HTTP 400 with instructions to select a server plan.

Admission academic mapping, main row, complete form data, snapshot and assignment audit commit together. The server rechecks the saved academic scope and locks the selected plan; it does not trust a picker result or amounts supplied by the client. A mismatched/unpublished/expired/foreign plan fails with 4xx and rolls back the admission write. Client component lists and totals are replaced by server snapshot values in formData.fees. The admission's admissionFeeAmount comes from the ADMISSION_FEE component.

Create/update/detail responses add:

- `feeStructureId`: selected master ID, or null for a legacy/unassigned admission.
- `academicFeePlan`: admissionId, feeStructureId, version, assignedAt, assignedBy, and `plan` containing the frozen complete plan.

`GET /api/v1/student-admissions/{admissionId}/fee-plan` retrieves the saved snapshot with college authorization. Never reconstruct an existing admission's fees by fetching the current master plan. An omitted selected ID on later saves preserves its existing snapshot; it never clears or refreshes it. The same plan ID keeps its old snapshot after archival. A different plan can be explicitly assigned only while the existing admission is Draft or Registered; replacing an existing snapshot requires feePlanChangeReason. Assignment history is retained. Changing academic scope through the separate academic-details endpoint cannot silently invalidate a fee snapshot.

For compatibility, legacy admissions without any selected shared plan remain supported. Editing or retrieving an admission requires a real academic college mapping; an old admission with no college mapping must be mapped to its actual college before using these scoped flows. Selecting a plan is optional for these existing contracts; this release does not require all drafts or old admissions to acquire a new plan.

## Existing fee endpoints

Managed plan edits through the old `/fee-structures/{id}` update/delete/publish/assign routes return HTTP 409 and point to the new workflow. The old active fee-structures list excludes managed plans; consumers should use the new college-scoped plan endpoints. Old legacy fee structures retain their existing routes.

For snapshot-backed admissions, existing `/fee-structure` and `/fee-summary` GETs use the snapshot, returning its full components and total. The detail additionally includes `paymentSchedule` and `academicFeePlan`; both detail and summary expose `otherFee` for components outside TUITION_FEE, ADMISSION_FEE, HOSTEL_FEE and TRANSPORTATION_FEE. Manual legacy fee upsert/resolution returns 409 for these admissions and cannot overwrite the snapshot. Existing payment ledger amounts are read when available. This release does not create fee collection invoices, payment transactions or scholarships automatically.

## Errors

- 400: malformed/local ID, invalid money/scope, mismatched plan or required reason missing.
- 401: unauthenticated/inactive account.
- 403: cross-college request or missing live role/action permission.
- 404: plan not found within the authorized college, or admission not found.
- 409: illegal status transition, stale revision, overlapping published version, immutable-plan edit or conflicting snapshot scope.

Business errors use `{ "success": false, "message": "...", "correlationId": "..." }`. ASP.NET request-model binding errors use its existing HTTP 400 validation-problem response. Do not retry a 409 by overwriting state: reload the current revision or select a valid plan.
