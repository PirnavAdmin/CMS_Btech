# Authorization 503 investigation and correction — R5

## Confirmed findings
1. The exact response with statusCode:503 is generated by ModulePermissionMiddleware. Its previous try/catch included the downstream endpoint for Super Admin/profile bypass requests. A MySQL exception in onboarding, user listing or another endpoint could therefore be mislabeled as an authorization failure. The auth database connection was also held open for the endpoint's duration on those branches.
2. In the latest supplied dump, the legacy auth tables exist but the R3 user_module_permissions, user_academic_year_access and user_access_audits tables are absent. That is evidence about the dump, not the running database. The active database might already have the migration.
3. No affected URL/method, current correlation ID, runtime log or running database connection was supplied. The unavailable production dependency and successful retry are NOT confirmed here. Do not reuse the earlier invitation configuration correlation ID; it belongs to a different failure.

## Source fixes
- ModulePermissionMiddleware now completes its auth-only database operation and disposes the connection before invoking downstream middleware/controller code. Endpoint SQL failures reach central database exception handling with their own context.
- Genuine authorization DB failures are wrapped with a dependency stage and safe connection-target metadata (server/port/schema only). Active-role, account, permission ceiling and college restrictions remain in place.
- Account readiness, effective-access snapshot and year authorization queries use the same typed failure path.
- ExceptionMiddleware logs the underlying exception, dependency, server/port/database, MySQL error number, SQL state, path/method and correlation ID. It returns a safe diagnostic code and correlation ID. No connection-string password/token is added to responses or diagnostic logs.
- Access-snapshot failures throw to the central handler so the API action sanitization filter does not erase these diagnostics.
- X-CMS-Build reports cms-backend-20261102-authorization-diagnostics-r5 even when the access snapshot is unavailable. X-Correlation-ID and response correlationId identify the matching log event.

## Steps on the running API host
1. Deploy only after successful dotnet build BTech.csproj -c Release. Restart the API process actually targeted by ngrok/proxy. Preserve runtime environment settings, SMTP and PasswordSetup__BaseUrl. Check X-CMS-Build on a response to identify the running assembly.
2. Run `Database/AdminManagement/Authorization_Preflight.sql` after selecting the same MySQL server/schema used by the effective DefaultConnection. It prints a connection probe, expected table/column inventory and permission catalog state. It changes neither data nor schema. Ideally run with the API database account; DBA metadata visibility is not proof of API SELECT privileges.
3. For a closer connection/SELECT check, run the read-only diagnostics project with the SAME environment and user secrets as the service:
   `dotnet run --project Tests/AuthorizationDiagnostics/AuthorizationDiagnostics.csproj -- --contentRoot <absolute-path-to-Backend>`
   Supply the content root path from your deployment. The project shares the backend UserSecretsId and reads appsettings/environment configuration. If the service uses deployment-only secret injection, use that same configuration for this process. The diagnostic never prints the connection password or user records. It does not build/start the API host and does not run migrations.
4. If tables/columns from the onboarding migration are missing, run the existing `Database/AdminManagement/User_Access_Onboarding_Migration.sql` on that schema, then rerun preflight. Do not reimport the full database dump. If a legacy authorization table/column is missing, restore its matching baseline migration; the onboarding migration creates its own additions only.
5. If connectivity or grants fail, fix the actual server/port/database/credentials and least required database grants on the host. A successful DBA login is not equivalent to a successful API-account login.
6. If permission_modules rows are missing/disabled, review the intended catalog and matching existing permission setup scripts/backups. Missing catalog entries generally cause 403, while missing tables/invalid columns or connectivity issues can cause 503. Do not blanket-grant permissions or disable auth to suppress the symptom.
7. Retry the exact affected request. For a GET, set CMS_BASE_URL, CMS_AFFECTED_PATH and CMS_AUTH_TOKEN locally and run `python Verification/Authorization/retry_get.py`. It prints status and correlation IDs, not account records/tokens. For POST/PUT/PATCH, retry through the existing frontend only after checking whether prior attempts created data, and copy Network Response plus X-Correlation-ID.
8. Read the log from the running process for that correlation ID. Example PowerShell:
   `.\Verification\Authorization\Find-Correlation.ps1 -CorrelationId <response-ID> -LogDirectory .\Logs`
   If log path is overridden, use the actual configured directory or service console output.
9. Success requires the intended endpoint response (e.g. HTTP 200 for a GET), a matching request-completed log and expected data/scope. Also test ordinary role permission and cross-college denial. Source packaging is not proof of a production fix.

## Response and log contract
Response fields: success:false, message:<safe actionable guidance>, code:<category>, statusCode:503, correlationId:<request ID>.
Categories: AUTHORIZATION_SCHEMA_INVALID; AUTHORIZATION_DATABASE_ACCESS_DENIED; AUTHORIZATION_DATABASE_NOT_FOUND; AUTHORIZATION_DATABASE_UNAVAILABLE.

Server log template (not a real captured log):
`Authorization dependency failed. CorrelationId=<request-ID>, Method=<method>, Path=<path>, Dependency=<stage>, Server=<server>, Port=<port>, Database=<schema>, MySqlCode=<number>, SqlState=<state>` followed by the actual underlying exception. Error 1146 indicates missing table; 1054 missing column; 1045 credentials; 1044/1142/1143/1227 database/operation privileges; 1049 wrong/missing schema; 1267/1271 incompatible collations. Use the actual error text to distinguish other connection/time-out failures.
